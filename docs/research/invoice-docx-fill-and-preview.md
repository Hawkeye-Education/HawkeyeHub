# Research: Filling the Official Receipt `.docx` and previewing it in a Plugin UI

Resolves #192. Feeds the Invoice Plugin spec (map #187).

Researched 2026-11-01. Each claim is tagged **[verified]** (run here, output quoted), **[source]** (stated by a primary source, linked) or **[inferred]** (our reading, not stated anywhere). Probes ran in Node 22 against a stand-in template built with the bilingual labels from #187. The real template was not used, because it does not belong in this public repo.

## TL;DR

- **Fill the template with the `docx` package we already ship. Use its `patchDocument`, not its `Document` builder.** Version 9.10.0, the one Receipt Extractor pins, fills `{{placeholders}}` in an existing `.docx`. It also repeats table rows for line items (`PatchType.TABLE_ROWS`), handles a placeholder that Word split across runs, and with `keepOriginalStyles: true` keeps the template's run formatting, including the `w:eastAsia` font. This adds no new dependency, and the patch-only import is smaller than what Receipt Extractor bundles today (48 vs 68 KiB gzip). **[verified]**
- **Preview by rendering the generated bytes with `docx-preview`** (Apache-2.0, about 50 KiB gzip with its `jszip`). The Preview then shows the exact file Save writes. An HTML replica would be a second copy of the layout, and it would drift from the template. **[verified]** for rendering and the CJK text, **[source]** for its limits.
- docxtemplater works too, and loops and conditions are in its free MIT core. But it adds about 85 KiB gzip of new dependencies (pizzip, pako, @xmldom/xmldom) for nothing `docx` lacks here. Rebuilding the layout in code, or doing a raw XML string replace, is worse on maintenance or correctness. **[verified]**
- **One precondition for the driving dev:** bundling the template means committing it to this **public** repo and shipping it in public GitHub Releases (ADR 0005). It needs a one-time edit in Word that types the placeholders in. Confirm the company is fine with the template's content being public.

## 1. Options for producing the `.docx`

### 1.1 Rebuild the layout with `docx`'s `Document` builder (today's Receipt Extractor approach)

`plugins/receipt-extractor/ui-src/docx.ts` builds its document from `Document`, `Paragraph` and `ImageRun`. For the Invoice, that would mean re-creating every part of the template in TypeScript: the title block, the bilingual labels, the line-item table with its borders and widths, the checkbox row, the Signature and Company Chop boxes, and the footer notes.

- Bundle: the builder's import (`Document, Packer, Paragraph, Table, TableRow, TableCell, TextRun`) is 228 KiB minified, 68 KiB gzip. **[verified]** (esbuild, `--minify`, gzip -9)
- Fidelity: it matches only as well as someone copies the template by hand. Every change to the template is a code change and a Plugin release. **[inferred]**
- Licence: MIT. **[source]** ([npm](https://www.npmjs.com/package/docx))

### 1.2 Fill the bundled template with `docx`'s `patchDocument` (recommended)

The `docx` patcher "allows you to modify existing documents". Placeholders are written `{{my_patch}}`, and the `patches` keys leave out the braces. `keepOriginalStyles` "will preserve the styles of the patched text when set to true". Its `data` may be a `Uint8Array`, `ArrayBuffer` or `Blob`, among others. **[source]** ([docs/usage/patcher.md](https://github.com/dolanmiu/docx/blob/master/docs/usage/patcher.md))

`PatchType.TABLE_ROWS` "repeat[s] the rows of a table in the template, once for each row of data". The rows it repeats are the ones that hold `{{items.description}}`-style fields. Other rows, such as the header and a Total row, "are kept as they are". **[source]** (the JSDoc on `TableRowsPatch` in `docx@9.10.0/dist/index.d.ts`)

Probe (`docx@9.10.0`, the repo's pinned copy). The template has `Receipt No. 收據編號: {{rec` + `eiptNo}}` in **two runs** (the second one bold, the way Word splits runs), a table with a header row, an `{{items.description}} | {{items.amount}}` row and a `Total 總額 | {{total}}` row. Every run uses `rFonts ascii=Arial eastAsia=PMingLiU`. Output text (table cells joined with `|` here) **[verified]**:

```
Receipt No. 收據編號: OR-2026-0001
Description 項目 | Amount (HKD) 金額
學費 Tuition     | 1,200.00
教材 Materials   | 100.00
Total 總額       | 1,300.00
rows: 4   eastAsia kept on filled runs: 23
```

The filled run came out as `<w:rPr><w:rFonts w:ascii="Arial" w:eastAsia="PMingLiU" w:hAnsi="Arial"/></w:rPr><w:t xml:space="preserve">OR-2026-0001</w:t>`, so it kept the template's font, and no `{{`/`}}` were left over. Traditional Chinese values (`陳大文`, `壹仟貳佰元正`) and the ☑ / ☐ characters passed through unchanged. **[verified]**

How each template field maps to this approach **[inferred]**:

| Field | Placeholder in the template |
|---|---|
| Receipt No., Date, Received from, Student Name, Total, Amount in words, Received by Name | `{{receiptNo}}` and so on, one `PARAGRAPH` patch each |
| Line items | `{{items.description}}`, `{{items.amount}}` in one table row, one `TABLE_ROWS` patch |
| Payment Method ticks | `{{cash}} Cash 現金  {{bankTransfer}} Bank Transfer …`, each patched to `☑` or `☐` |
| Remarks | `{{remarks}}`; a multi-line value is one patch with `TextRun({ break: 1 })` runs |
| Signature, Company Chop, footer notes | not touched; they stay as the template has them |

- Bundle: the patch-only import (`patchDocument, PatchType, TextRun`) is 151 KiB minified, 48 KiB gzip. Builder and patcher together are 73 KiB gzip. **[verified]**
- New dependencies: none. `docx` is already a devDependency (Vite bundles it into `ui/`), and its own `fflate` does the unzipping. **[verified]** (`npm view docx dependencies`: `fflate`, `nanoid`)
- Maintenance: `dolanmiu/docx` has about 6.0k stars and 2 open issues, and was pushed 2026-10-31. The latest release is 9.15.1. **[source]** (GitHub API, npm)
- Loading the template: the Plugin UI is served from `hawkeye-plugin://<id>/` (PLUGIN_STANDARD §4.1), so `fetch(new URL('./official-receipt.docx', import.meta.url))`, or a Vite `?url` import, reads the bundled file as an `ArrayBuffer`. Save then goes through `<a download>` with the Blob, as Receipt Extractor's does. **[inferred]**
- **Gotcha:** if the template's checkboxes are Word content-control checkboxes or Wingdings `w:sym` glyphs, replace them with a `{{cash}}`-style placeholder once in the template. The patcher replaces text, not symbols. **[inferred]**

### 1.3 Fill the bundled template with docxtemplater + pizzip

- Free core, MIT: "{tag} replacement, Conditions, Loops, and Change delimiters". Every other module (Image, Html, Table, Styling, …) is paid, from 500 € a year. **[source]** ([pricing](https://docxtemplater.com/pricing/))
- A loop whose start is in a row's first cell and whose end is in its last cell repeats that row. Inverted sections `{^x}` render when the key is false or empty. A tick could therefore be `{#cash}☑{/cash}{^cash}☐{/cash}`. **[source]** ([tag types](https://docxtemplater.com/docs/tag-types/))
- Probe: same template with `{receiptNo}` split across runs and `{#items}{description} | {amount}{/items}` in one row. All values filled, PMingLiU kept, the table grew to 3 rows, nothing left over. **[verified]**
- Bundle: `docxtemplater` + `pizzip` is 284 KiB minified, 85 KiB gzip. All of it is new: `@xmldom/xmldom`, `pizzip` and `pako`. **[verified]**
- Licence: docxtemplater MIT. pizzip is `(MIT OR GPL-3.0)`, so take it under MIT. **[source]** (npm)
- Maintenance: about 3.6k stars, 5 open issues, pushed 2026-10-15. **[source]** (GitHub API)

It is as capable as 1.2 for this template, but costs a new dependency tree. **[inferred]**

### 1.4 Edit `word/document.xml` directly with a zip library

`fflate` (MIT, already inside `docx`) unzips and zips in 6 KiB gzip, and the browser's `DOMParser`/`XMLSerializer` read and write the XML. **[verified]** (bundle) A probe doing `replaceAll('{{receiptNo}}', …)` **missed the split placeholder**: `OR-2026-0001` never appeared and `{{rec`/`eiptNo}}` stayed in the output. **[verified]** To make this robust you would have to write run-merging, XML escaping and row cloning yourself, which is what 1.2 already does. Not worth it.

## 2. Options for the Preview

### 2.1 Render the generated `.docx` with docx-preview (recommended)

- Goal: "render/convert DOCX document into HTML document with keeping HTML semantic as much as possible". The README says it "is limited by HTML capabilities". Only `renderAsync` is stable API. **[source]** ([README](https://github.com/VolodymyrBaydalka/docxjs))
- Pages break only at manual page breaks, `lastRenderedPageBreak` (opt-in) or section changes. "Realtime page breaking is not implemented", and fields "[are] not supported yet". **[source]** (README) A one-page receipt needs neither. If the template's footer uses a PAGE field, that field will not render. **[inferred]**
- Probe: the patched `.docx` from 1.2, rendered in happy-dom, gave text containing `正式收據`, `陳大文`, `壹仟貳佰元正`, `OR-2026-0001` and `☑`. **[verified]** Pixel layout was not checked; that needs a real Chromium.
- Chinese text: `parseFont` turns `rFonts` into `font-family: <ascii>, <asciiTheme>, <eastAsia>`. Chromium then draws Latin text in the ascii font and falls back to the eastAsia font for CJK glyphs the ascii font lacks, which roughly matches Word. **[source]** (`docx-preview.mjs` `parseFont`; [inferred] for the comparison with Word) It also loads fonts embedded in the `.docx` (it de-obfuscates `embedRegular`) and renders `w:sym` glyphs in their named font. **[source]** (same file) A font missing from the machine, such as PMingLiU on a Mac without Office, is substituted in both the Preview and Word. That is a property of the machine, not of the Preview. **[inferred]**
- Safety: document text goes in as DOM text nodes. `innerHTML` is used only to clear its containers and for one `&nbsp;`. **[source]** (same file) That fits PLUGIN_STANDARD §4.4's `textContent` rule in spirit.
- Styling: it injects a `<style>` with the document's own fonts and colours. That is the document's look, not the Plugin's chrome, but it sits awkwardly with §4.3's rule against literal colours and fonts. Render it inside its own container (or a shadow root) so it cannot leak into the Hub styles. **[inferred]**
- Bundle: 171 KiB minified, 50 KiB gzip, including its `jszip` dependency (30 KiB gzip). jszip 3.10.2 is already in the workspace as a test devDependency. Patcher plus preview together come to 98 KiB gzip. **[verified]**
- Licence: Apache-2.0 (package `LICENSE`, no `NOTICE` file). jszip is `(MIT OR GPL-3.0-or-later)`, so take it under MIT. **[source]**
- Maintenance: about 2.1k stars, 101 open issues, pushed 2026-09-21, version 0.4.1. It is the least active of the libraries here, so pin it exactly, as the repo already does for every dependency. **[source]** (GitHub API, npm)

### 2.2 An HTML replica of the receipt

No dependency, and it gives full control over the Hub's styling. But the Preview would then come from different code than the file it previews. Any template edit, or any difference in how the two sides lay out text, makes the Preview wrong without anyone noticing. That defeats #187's "a Preview before anything is saved". **[inferred]**

## 4. What the spec still has to decide

- Whether the prepared template, with its placeholders, may be committed to this public repo and shipped in public Releases.
- The placeholder names, as part of the `Invoice` model. A unit test could feed `patchDetector` (also in `docx`) the bundled template and assert that its keys equal the model's fields, so a template edit cannot silently drop a field. **[source]** for `patchDetector` (`index.d.ts`), **[inferred]** for the test.
